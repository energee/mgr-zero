## Overview [#overview]

MGR has one HTTP endpoint. No resource URLs, no verb shopping. You POST an
operation name and its input, and the response is always the same envelope.
Everything else in this section is a rule that holds across every operation,
or the operations themselves.

### The endpoint [#endpoint]

Registered operations are either queries (side-effect-free reads) or commands
(writes):

```http
POST /api/command
content-type: application/json

{
  "breweryId": "<uuid>",
  "name": "<operation name>",
  "input": { },
  "requestId": "<uuid, commands only>",
  "expectedContext": { "actorId": "<uuid>", "breweryId": "<uuid>", "customerId": "<uuid, portal only>" },
  "origin": "<ui or chat; defaults to ui>",
  "conversationId": "<uuid, chat commands only>",
  "previewToken": "<uuid, chat commands only>"
}
```

`name` and `input` are always required. `breweryId` is required for tenant
operations and must be omitted for `provision_brewery`, the sole authenticated
pre-tenant command. `requestId` is required for
every command and optional for queries. See [idempotency](#idempotency) for why
it exists and what reusing one does.

`expectedContext` is optional for explicit bearer-token clients. The browser app
includes it from the verified context that rendered an action and keeps it with
an uncertain retry. It is a restriction, not identity proof: authentication and
membership checks still decide what the caller may do. When supplied, its actor,
brewery, and optional customer must match the authenticated request before the
operation runs.

`origin` defaults to `ui`. A `chat` command must include both `conversationId`
and `previewToken`. The server issues that token from `preview_command` after it
validates and canonicalizes the proposed input for the signed-in author,
brewery, conversation, and registered write. A token cannot confirm another
input or conversation. Retrying the confirmed command with the same `requestId`
returns its original result even after the preview expires or stock changes and
does not append a second history result. For `record_movement`, the preview
returns signed units, frozen barrel volume, selected bin/lot stock before and
after, displayed SKU/package/location labels, channel tax, destination warnings,
and the lawful correction. Commit locks the inventory ledger and those displayed
dependencies, rebuilds the authoritative snapshot in the same database
transaction, and returns `409 conflict` if anything changed. A stale refusal
leaves no movement, completed request, or conversation result.

The current staff browser composer is a structured client of this same endpoint. It
loads only the registered reads allowed for the current staff role, asks for every
required movement field, calls `preview_command`, and sends `record_movement`
only after the person selects **Commit movement**. Editing or dismissing a
proposal sends no movement command. Staff ATP answers use `get_atp`; portal
domain operations remain limited to the registered `portal_*` surface and no
composer is mounted in the customer shell. Conversation lists and messages are
staff-only, server-owned, author-and-brewery scoped, and contain no credentials
or model transcripts. No model, voice provider, alternate write route, or
client-local conversation history is involved.

The endpoint accepts at most **8 MiB** of JSON per request and admits **120
requests per authenticated account per 60 seconds**. The account budget is
shared by cookie and bearer authentication, every brewery, and the pre-tenant
provisioning command. A `429` response includes `Retry-After` in seconds. The
limit protects this command endpoint; it is not an IP or general Data API
limit. The 5,000-row CSV limit is separate, so imports with unusually large
string cells may need to be split into smaller batches.

### Responses [#responses]

Success carries the operation's result in `data`:

```json
{ "ok": true, "data": { }, "requestId": "…", "correlationId": "…" }
```

Failure carries a code and a message instead:

```json
{ "ok": false, "error": { "code": "not_found", "message": "…" }, "correlationId": "…" }
```

Every response, success or failure, has a server-generated `correlationId`.
Log it. That is the value that ties your client's view of a request to the
server's. A command's response also echoes the `requestId` you submitted, so a
queued write can be matched to its result without keeping the request body
around.

Status codes and every `error.code` are on the [errors page](#errors).

### Calling it [#calling]

Every example in this section uses two variables: `MGR_URL` is the origin the app
is served from (`http://localhost:3000` in development), and `MGR_TOKEN` is a
Supabase access token for a member of the brewery (or any authenticated account
for `provision_brewery`).

```bash
curl -X POST "$MGR_URL/api/command" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $MGR_TOKEN" \
  -d '{ "breweryId": "…", "name": "list_brands", "input": {} }'
```

From the browser the app calls the same endpoint through `lib/commands/client.ts`,
which generates the `requestId` and unwraps the envelope, throwing on failure:

```ts
import { command } from "@/lib/commands/client";

const order = await command(breweryId, "create_order", {
  kind: "wholesale",
  fromLocationId: warehouseId,
  lines: [{ skuId, qty: 10 }],
});
```

The optional sixth argument carries provenance for a confirmed composer write:

```ts
await command(breweryId, "record_movement", input, requestId, expectedContext, {
  origin: "chat",
  conversationId,
  previewToken,
});
```

The customer portal's invoice-payment handoff is a session-authenticated `GET`
instead of a registered operation. It authorizes one current live invoice only
when QuickBooks has reported a positive balance, reads its payment link on the
server, rechecks the balance and access, and redirects without returning or
storing that bearer link in the command API. A zero or unknown current balance
leaves payment unavailable; a reopened invoice with a positive balance remains
eligible even when its history retains an earlier paid date. A reconnect,
credential rotation, or loss of the required accounting permission while the
link is being fetched also leaves payment unavailable.

The public website-menu feed is the other narrow `GET` exception:
`/api/public/menus/{publicId}`. Its opaque id selects one configured POS
location, and the response contains only its location name, a deterministic
`version`,
and explicitly published, currently stocked rows with `brand`, `format`,
`ounces`, `priceCents`, and `available`. It exposes no tenant, catalog, stock,
bin, channel, connection, or provider identifiers. Successful responses set
`Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate=300`;
the quoted version is also its `ETag`, and a matching `If-None-Match` receives
`304` with the same cache headers. Missing ids and failures are not cached. The
endpoint allows cross-origin `GET` and `OPTIONS`, exposes `ETag`, and accepts
`If-None-Match`; its 200, 304, 404, and 503 responses all carry the same safe
wildcard origin policy. It does not accept writes.

Outside the app, the equivalent is a POST with your own `requestId`:

```ts
const requestId = crypto.randomUUID();
const res = await fetch(`${MGR_URL}/api/command`, {
  method: "POST",
  headers: { "content-type": "application/json", authorization: `Bearer ${token}` },
  body: JSON.stringify({ breweryId, name: "create_order", requestId, input }),
});
const { ok, data, error } = await res.json();
```

### Availability [#availability]

Operations are listed by area, each marked with its status. **Available**
operations are registered today and the endpoint answers them. Each one lists
the roles that may call it, its fields, and an example request. **Designed**
operations are ones the screens need that the backend has not built. Calling
one returns `404 unknown_command`.

Both lists are generated from the command registry and from the screens, so
neither can drift from the product. The designed list is the roadmap: what is
coming, and which screen is waiting on it. No dates.

## Authentication & roles [#authentication]

Every request identifies a caller. Tenant operations also identify a brewery. The caller proves who they are
with either the Supabase cookie session the app's login flow establishes, or an
access token:

```bash
curl -X POST "$MGR_URL/api/command" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $MGR_TOKEN" \
  -d '{ "breweryId": "…", "name": "list_brands", "input": {} }'
```

`provision_brewery` requires authentication but no existing membership; omit
`breweryId`. Its blank tenant-role cells below mean roles do not apply, not that
access is anonymous. All other operations use the following membership checks.

The `breweryId` in the body then decides *which* brewery the caller is acting
in. Being signed in is not enough. The caller must be a member of that brewery:
staff (`brewery_users` with role `admin`, `sales`, `warehouse` or `brewer`) or
a portal user (`customer_users` linked to one of the brewery's customers, role
`customer`).

The two failures are different, and that difference is worth handling.
`401 unauthenticated` means the token is missing or expired: sign in again.
`403 not_member` means the token is fine and the `breweryId` is wrong.
`409 context_changed` means a supplied `expectedContext` no longer matches;
return to that original account and workspace to retry an uncertain write.

### Roles are enforced twice [#enforcement]

An operation lists the roles that may call it. The endpoint refuses the rest
with `403 permission_denied` before the handler runs. Below that, Postgres
row-level security scopes every query to the caller's brewery, so a role that
slipped through would still read nothing. That matters when you are debugging an
empty result: an empty list and a forbidden read look the same from outside, on
purpose. A caller cannot probe another tenant's data by watching which ids
return `404` rather than `403`.

A portal user sees only their own customer's records. That is why the portal
operations are a separate set, not the staff ones with a filter applied.

## Idempotency & retries [#idempotency]

A network that drops a response has not told you whether the write happened.
Retrying blindly risks a duplicate order. Not retrying risks losing one. The
`requestId` removes the guess.

Every command (every write) must carry a client-generated RFC 9562/4122 UUID as
`requestId`. Queries may omit it. A repeated read costs nothing.

```ts
const requestId = crypto.randomUUID();   // once, before the first attempt

async function submit() {
  return fetch(`${MGR_URL}/api/command`, {
    method: "POST",
    headers: { "content-type": "application/json", authorization: `Bearer ${token}` },
    // The same requestId on every attempt. That is what makes the retry safe.
    body: JSON.stringify({ breweryId, name: "create_order", requestId, input }),
  });
}
```

### The three outcomes [#outcomes]

Reusing a `requestId` with the **identical payload** is the safe retry: the
server recognises the write it already did and answers with the original result
rather than performing it twice.

Reusing one with a **different payload** is `409 conflict`. That is the endpoint
telling you two different writes are wearing the same id. Almost always a
client that generated the id once and then mutated the form.

A **new** `requestId` is a new write, every time. Generating one inside your
retry loop rather than outside it is the single most common way to create
duplicate orders, because each attempt then looks like a fresh intention.

Offline eligibility is narrower than idempotency. The browser currently queues
only `record_fermentation_reading`, after persisting its exact input,
observation time, request ID, actor, brewery, and role before transport. A
reload or reconnect retries that same envelope. `record_movement`,
`record_pick`, and stock transfers require current server state and are never
queued; a stable request ID alone does not make an operation safe offline.

This holds for every command that writes through a ledger RPC. Five do not yet:
`set_notification_preference`, `set_brewery_quiet_hours`,
`set_notification_destination`, `consume_chat_link_proof`, and
`unlink_chat_user` still require a `requestId`, but nothing on the server
checks it. A retry with a different payload lands as `200`, not `409`. Treat
those five as not-yet-idempotent until this note is removed.

### Where to generate it [#where]

Generate the id at the moment the user commits (pressing Submit), not when the
request is built. `lib/commands/client.ts` does exactly this in the app: one id
per invocation, reused by any transport-level retry underneath it.

Timeouts and `5xx` responses are the cases worth retrying, with the same id.
A `4xx` other than `409` will not change on retry. Fix the request instead.

## Errors [#errors]

A failure is the same envelope as a success, with `ok: false`:

```json
{
  "ok": false,
  "error": { "code": "conflict", "message": "requestId reused with a different payload" },
  "requestId": "11111111-1111-1111-1111-111111111111",
  "correlationId": "…"
}
```

Branch on `code`, never on `message`. The code is a contract. The message is
written for a person and will be reworded. Both are safe to show a user. The
endpoint never returns raw database text, which is why an unmapped database
failure arrives as a generic `db_error` while the detail goes to the server log
under the same `correlationId` you were given.

Every response carries a `correlationId`, success or failure. Log it. It is the
one value that ties what your client saw to what the server recorded.

### Validation failures name their fields [#validation]

`invalid_input` messages are generated from the operation's schema, one line per
problem:

```
validation failed: ✖ Invalid UUID → at customerId
```

So a 400 is usually actionable without reading anything else. Each operation's
field table lists the same types the validator enforces.

## Conventions [#conventions]

These hold across every operation, so they are stated once here rather than
repeated in each field table.

**Field names are camelCase** in `input`, even though the database columns they
land in are snake_case. Response payloads come back in the database's own shape,
so a field you send as `skuId` reads back as `sku_id`. That asymmetry is real.
Handle it in one mapping layer rather than at each call site.

**Ids are UUIDs** wherever the id belongs to MGR: every record you create, read,
or reference here. The exception is an id minted by somebody else and stored as
it arrives. `externalDestinationId` on `set_notification_destination` is a Slack
channel id, and its field table says `string` for that reason. Read the table
when it disagrees with this line. The table is generated from the schema. This
sentence is not.

**Money is integer cents.** `unitPriceCents: 1250` is $12.50. There are no
floats in prices anywhere in the API, because a fraction of a cent that survives
a few multiplications becomes a discrepancy on an invoice.

**Dates are `YYYY-MM-DD` strings**, not timestamps, wherever the field means a
calendar day. A requested ship date is a day, not an instant. Fields that
genuinely mean an instant, such as `now` on `get_today`, take an offset-aware
ISO timestamp so the server never has to guess a timezone.

**Volumes are numeric strings.** `bblPerUnit` is `"0.1651"`, not `0.1651`. A
barrel figure feeds excise reporting, and binary floating point cannot represent
most decimal fractions exactly. Passing it as a string keeps the exact decimal
the brewery entered all the way to the tax form.

**`limit` defaults to 50 and caps at 200** on every operation that takes one.

### Fields the server computes [#computed]

Some values are derived and must not be sent. `bbl` on an inventory movement is
computed from the SKU and the quantity. A field an operation does not declare is
dropped before the handler runs rather than trusted, so sending your own `bbl`
does not fail. It is simply ignored, because two sources for one number is how
ledgers drift. Read the computed value back rather than assuming yours was used.

Prices on order lines are snapshotted at creation from the customer's price
group. You do not send them, and changing a price group later does not rewrite
an existing order.

### Nothing is edited in place [#append-only]

The inventory ledger is append-only: a correction is a new movement in the
opposite direction, never an edit. Invoices work the same way. A credit memo is
negative lines at the original prices. Where you might expect an update or a
delete, look for the compensating operation instead.

`operations_digest`. A preference enables or mutes one reason for the calling

top of them.

### Orders & invoicing [#orders]

An order moves `draft → submitted → confirmed → picked → shipped`, or
`cancelled` any time before shipping. Line items are `{ skuId, qty }` and prices
are snapshotted from the customer's price group when the order is created, so a
later price change never rewrites an existing order. Mutations return
`{ order_id }` unless noted otherwise.

Confirming creates allocations and returns `{ order_id, warnings }`, where
`warnings` is `[{ sku_id, atp }]` for any SKU whose available-to-promise went
negative. These are soft warnings. The confirm still succeeds, because the
brewery, not the API, decides whether to oversell.

Shipping is one transaction: inventory movements, allocation fulfilment and
(unless deferred) the invoice, returning `{ order_id, invoice_id }`.
`invoiceTiming: "on_delivery"` ships without invoicing yet — `invoice_id`
comes back null, and `confirm_delivery` invoices later at the shipped
quantities and order prices. A credit memo reverses
part of an invoice as negative lines at the original prices plus return-in
movements. Invoices are never edited.

### Inventory & locations [#inventory]

`reverse_inventory_movement` accepts only standalone adjustments and losses. Its required note and selected movement form the retry identity; it appends an exact linked opposite with frozen package class and volume in the original bin and lot. Insufficient stock prevents removing a positive adjustment. Count/depletion and compound correction owners remain unchanged. Completed retries return the original result; changed inputs conflict. Corrections post in their own period and never rewrite filed snapshots.


The ledger is immutable. A movement is appended, never edited or deleted, and a
correction is a new movement in the opposite direction. That is what makes the
history admissible for excise reporting. `bbl` is computed server-side from the
SKU, so a caller must not send it.

On-hand is the sum of movements per SKU and location. Available-to-promise is
on-hand minus open allocations: the number a salesperson should be shown before
promising stock.

A stock transfer moves finished goods, materials, or empty kegs between two of
the brewery's locations, bin to bin, without an order or an invoice.
`create_stock_transfer` refuses a transfer whose source and destination
location are the same — move within one location with `move_stock_bin`
instead. `receive_stock_transfer` posts every line's paired ledger rows in one
transaction, so a transfer is never left half-received.

### Catalog & pricing [#catalog]

A brand is the beer's sellable identity — name, style, ABV, tax class. A
format is the physical package (keg, can, bottle); it owns `unitsPerCase` and
`bblPerUnit`. A poured format (a pint, a taster) never holds stock: it is a
ratio back to the keg it pours from, and never becomes a SKU. A SKU is one
brand × one packaged format, with an optional UPC.

Prices live on a grid, not on SKUs. A price group is a row of that grid and a
brand sits on one; a sale channel is the column and a customer sits on one.
`set_channel_price` fills one cell — sale channel × price group × format —
with an integer `unitPriceCents`, and every SKU of that group and format sells
at it on that channel. `clear_channel_price` empties the cell, which unprices
those SKUs on that channel. There is no per-SKU exception.

### Customers [#customers]

A customer is a distributor, retailer, brewery, or other account, carrying a
two-letter `state`, a required sale channel (which decides its prices), and an
optional licence number and payment terms.
`upsert_customer` creates when `id` is omitted and updates when it is present.

Ship-to addresses matter beyond delivery. The state on the ship-to drives excise
destination reporting, so an address is a compliance record, not just a label.
Portal orders ship from one warehouse per brewery, set with
`set_portal_fulfillment_source`. Portal ordering fails until that is set.

`invite_customer_user` is available to Admin and Sales. It emails a new Auth
account and attaches buyer membership to the specified customer. Existing
Auth emails conflict; there is no existing-account attachment or resend flow.
Keep the same request ID and input after an interrupted invitation; completion
reuses the saved user identity. Replaying a completed invite never restores
revoked membership.

### Taproom & kegs [#taproom]

Physical counts are available to Admin, Warehouse, and Taproom through the commands below and the live **Taproom** page. Prepare a complete snapshot, then submit every explicit bin/SKU/lot bucket with its revision and today's brewery-local date. `lotId: null` names untracked stock, never automatic allocation. Quantities are remaining whole packages; a partial keg counts as one until gone. Matching counts persist without movements. Shortages alone post exact-bucket depletion, with the tenant's Taproom channel tax treatment and volume frozen at posting; POS does not change the posting. `list_taproom_counts` returns only the newest 50 headers for one owned taproom; use `get_taproom_count` for a complete durable receipt with safe bin and SKU labels independent of list-query row caps.

`get_taproom_print_labels` accepts the exact prepared revision and returns only current positive Taproom stock, retaining each bucket's row number from the complete count worksheet. It supplies safe bin, SKU, brand and package labels plus a tracked lot UUID and code, or untracked, and quantity. A changed revision is refused. Full lot history remains outside this projection, and the query neither posts inventory nor claims a command request.

Changed stock, prior count, or brewery-local date requires refreshing the snapshot. Omitted, duplicate, extra, fractional, negative, overcount, historical and same-day repeat submissions are refused. An unchanged request ID returns the original result before these freshness checks; changed payload reuse conflicts. A timeout or `5xx` leaves the exact count request frozen for retry, while a definitive first validation refusal allows correction. `correct_taproom_count` lets Admin replace only the latest uncorrected root count when at least one submitted line was counted too low. Every changed quantity must be a whole increase no greater than its frozen quantity before the count, and a reason is required. The correction preserves the root observation time, appends exact frozen compensation and smaller replacement legs in the correction's audit period, supplies one effective receipt and next-count baseline, and leaves original and filed records unchanged. Warehouse and Taproom may read the effective receipt and correction audit but cannot run the correction. An uncertain response keeps the exact request frozen for replay. Generic inventory adjustments do not reverse count depletion. Direct raw lot history remains unavailable; use the checked current-stock print projection to match a physical tracked lot without guessing.

`get_taproom_draft_projection` compares an unsaved recount with expected consumption from the latest effective saved count's observation time through the response's server `as_of`. It identifies that baseline and both bounds, groups expected BBL by brand, and reports coverage-source bounds and completeness, unmapped and ignored lines, excluded shares, and unattributed poured volume. No saved baseline or usable POS observation leaves expected null; a complete empty observation may return zero. This live read never posts inventory, allocates lots, freezes a POS snapshot, or replaces the count snapshot revision, and late reconciled facts may change a later response.

A taproom holds stock like any other location, with two things a warehouse does
not have: a par level per SKU, and standing allocations that reserve stock
against a recurring need. Setting a standing allocation to zero releases it.

Replenishment reads the gap between par and on-hand and suggests a transfer
quantity. `create_replenishment_order` turns those quantities into an
already-confirmed taproom transfer, skipping the draft and submit steps a
wholesale order goes through.

Kegs are tracked as pools — owned, leased, or pay-per-fill — over a
location-grain event ledger. A leased or pay-per-fill pool names its vendor,
and a pay-per-fill pool also needs a per-fill cost; `update_keg_pool` only
changes the fields you send, and an inactive pool refuses new events.
`record_keg_event` posts one append-only row: quantity is always positive and
`reason` carries the direction (acquired, retired, shipped, returned, lost,
found). Shipped and returned require a customer; acquired, retired, and found
never carry one; lost may optionally name a customer, which reduces their keg
balance. Retired, shipped, and lost cannot take out more kegs than the bin
currently holds. Kegs moving between bins or locations go through the
transfer and movement commands, not this one, and a keg deposit refund is its
own credit memo.

### Purchasing & materials [#purchasing]

Materials are what the brewery buys rather than sells: grain, hops, cans, crowns,
labels. They carry their own on-hand and their own counts, separate from the
finished-goods ledger, because a shortfall in either stops a run for different
reasons.

A purchase order is drafted (optionally from computed material requirements),
sent to a vendor, then received. Receiving is what writes material stock, so an
unreceived PO never inflates what a packaging run believes it has.

long. Fermentation readings are appended per batch and are what an overdue
reading notification is measured against.

### Compliance [#compliance]

Compliance reads the same ledger operations write. A removal's destination state
comes from the ship-to on the order, brand approvals and state registrations say
where a beer may be sold, and loss is attributed to a cause rather than left as
an unexplained gap between what was brewed and what was sold.

Reports are generated from that history and then filed; generating one never
changes the underlying records. Filing refuses not only an exact repeat of a
period already on file but any period whose dates overlap one, in the same
jurisdiction — the guard is a date range, not an equality check.

Completion-loss review preserves the original generic-loss row. Each partial
allocation creates an equal signed pair, so the additive removal total changes
classification without changing total volume. `bbl` is positive, finite, and
limited to eight fractional digits. `destinationState` is required for
`sample` and must be omitted for `taproom` and `destruction`. Direct cellar
Taproom volume freezes the system Taproom channel tax treatment; generated
reports name the outstanding external mapping and filing refuses until that
mapping is separately approved. The cellar breakdown is explanatory and must
not be added to `figures.removals`.

{/* ops:compliance */}

### Team & brewery settings [#team]

Staff roles are `admin`, `sales`, `warehouse` and `brewer`, and every operation
in this reference lists the roles allowed to call it. A membership is what ties a
user to a brewery. Revoking one ends access without deleting the history that
member wrote.

`invite_staff` assigns one role and returns `{ userId }`. Invitation requests
retain their Auth identity through interrupted completion; retry unchanged
requests with the same ID. Changing the email, role, customer, actor, or brewery
is different intent. Existing accounts cannot be attached, and completed replay
does not restore revoked membership. The inviter must still have permission
when membership is completed.

`provision_brewery` omits `breweryId`; authenticated callers send name, a valid
timezone, and optional `ttb`. One transaction creates the brewery and first
admin membership and returns the brewery UUID. Replay returns that UUID without
restoring revoked membership. `MGR_DEDICATED=1` disables web creation only;
authenticated API provisioning remains available.

`import_csv` accepts 1–5000 string-field rows and returns
`{ committed, blocked, outcomes }`. Each outcome names its 1-based `row`,
`status` (`committed` or `blocked`), and its original `result` or `error`.
Dependent writes within one row commit together; independent rows may succeed
when another fails. Both successful and blocked outcomes are durable: resend
the identical kind and complete rows array with the same request ID to recover
the original results. Changed, appended, or removed rows conflict. Start a new
request containing only corrected blocked rows; posting committed opening
balances with a new ID adds stock again.

All import values are strings. Required fields precede the semicolon:

| Kind | Fields |
| --- | --- |
| `customers` | `name`, `type`, `state`, `saleChannelId`; `licenseNumber`, `paymentTerms` |
| `ship_tos` | `customerId`, `label`, `address1`, `city`, `zip`, `state`; `address2` |
| `products_skus` | `product`, `formatId`; `sku_name`, `style`, `abv`, `upc` |
| `channel_prices` | `saleChannelId`, `priceGroupId`, `formatId`, `unitPriceCents` |
| `opening_balances` | `skuId`, `locationId`, `binId`, `qty`; `note` |

Unknown row fields are rejected. References use explicit UUIDs; create missing
formats before importing. Product imports reuse an existing brand without
changing its metadata and create the SKU in the same row transaction. Duplicate
customer/SKU creation is blocked; channel-price rows set the existing grid cell.
Opening quantities are positive SKU-unit counts with a bin belonging to the
location. Prices are nonnegative integer cents, at most 2147483647.

### Customer portal [#portal]

Callers with the `customer` role are portal users, not staff. They see only
their own customer's data, and these are the only operations that role can call.
The scope is enforced server-side, not by which operations the client chooses
to show.

Portal orders are wholesale orders shipped from the brewery's warehouse, and
they move through the same lifecycle staff orders do. A portal user drafts,
updates, and submits. Confirming, picking, and shipping stay with the brewery.
