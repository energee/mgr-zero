title: "Compliance"
description: "Brand approvals, state registrations and licences, lot tracing and loss."
---

Compliance reads the same ledger operations write. A removal's destination state
comes from the ship-to on the order, brand approvals and state registrations say
where a beer may be sold, and loss is attributed to a cause rather than left as
an unexplained gap between what was brewed and what was sold.

Reports are generated from that history and then filed; generating one never
changes the underlying records. Filing refuses not only an exact repeat of a
period already on file but any period whose dates overlap one, in the same
jurisdiction — the guard is a date range, not an equality check.

Completion-loss review preserves the original generic-loss row. Each partial
allocation creates an equal signed pair, so the additive removal total changes
classification without changing total volume. `bbl` is positive, finite, and
limited to eight fractional digits. `destinationState` is required for
`sample` and must be omitted for `taproom` and `destruction`. Direct cellar
Taproom volume freezes the system Taproom channel tax treatment and files
once, as a removal under that treatment (`taxable` for the default channel:
taxpaid removals for consumption on premises). The cellar
breakdown is explanatory and must not be added to `figures.removals`.

For an ended period, `figures.inProcess` is beer remaining in tanks at the end
of `periodEnd` in the brewery's time zone, reconstructed from dated brew turns,
transfers, tank adjustments and packaging draws. Packaging draws count on the
lot's Packaged-on date. New ended-period reports include `figures.inProcessAsOf`,
the ISO period-end date. Current and upcoming periods instead show the live
balance to date and omit that field; this is not a forecast of their period end.
Older saved filings and correction records without that field retain their
original filing-time or correction-time tank quantities; they are never rewritten.

`search_colas` reads TTB's public COLA registry live, under the brewery's TTB
registry number from Settings; nothing it returns is stored. It answers
`{ permit, rows }`, each row carrying `ttbId`, `serial` (or `null`),
`completedOn` (`YYYY-MM-DD`), `fancifulName`, `brandName`, `classCode` and
`className`. A brewery with no registry number gets a 400 `bad_request`; a TTB
failure gets a 502 `upstream_unavailable`, so an empty `rows` is a real
no-match. COLAs completed more than 15 years ago are not found.

`get_cola_details` reads one TTB ID from TTB's public COLA detail page, live, under the brewery's TTB registry number; nothing it returns is stored. It answers `{ ttbId, permit, status, approvedOn, images }`, where each image has a `url` and a `label`. A COLA whose principal permit is not the brewery's gets a 403 `permission_denied`. A COLA that TTB does not report as `APPROVED` gets a 400 `bad_request`, and an approved COLA with no approval date gets a 502 `upstream_unavailable`.

`get_cola_image` renders one of those image `url`s as `{ dataUrl }`, a base64 data URL. The first view of a saved label checks the COLA in a fresh TTB session and keeps a copy of the label; later views return that copy without contacting TTB, for as long as the label stays saved on an approved, dated COLA. The image must be a JPEG, PNG, GIF or WebP no larger than 8 MiB, and it must be a label on an approved COLA under the brewery's permit. Admin and Sales may preview any such label. Other staff roles may read only an image that an approved, dated COLA already saves on one of their brewery's brands; an image not saved that way returns 404 `not_found`.

`upsert_brand_approval` takes `imageUrl`, a `url` from `get_cola_details`. The same request must also send `kind` `cola` and `approvedOn`, even on an edit; the endpoint does not read them from the stored record. Sending `approvedOn` as `null` clears the approval date and the stored image. Changing `ttbId` or `kind` removes an image that the request does not replace.
