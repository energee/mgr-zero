---
title: "Customers"
description: "Customer accounts, ship-to addresses and portal invitations."
---

A customer is a distributor, retailer, brewery, or other account, carrying a
two-letter `state`, a required sale channel (which decides its prices), and an
optional licence number and payment terms.
`upsert_customer` creates when `id` is omitted and updates when it is present.

Ship-to addresses matter beyond delivery. The state on the ship-to drives excise
destination reporting, so an address is a compliance record, not just a label.
Portal orders ship from one warehouse per brewery, set with
`set_portal_fulfillment_source`. Portal ordering fails until that is set.

`invite_customer_user` is available to Admin and Sales. It emails a new Auth
account and attaches buyer membership to the specified customer. An email
that already has a confirmed Auth account instead gets a pending invitation:
the command returns `{ inviteId, state: "pending_consent" }`, and membership is
granted only when that account signs in and calls `accept_account_invitation`
(see [Team](/docs/api/team)). The command conflicts only when that account
already belongs to the customer or an invitation for the email is already open.
There is no resend flow.
Keep the same request ID and input after an interrupted invitation; completion
reuses the saved user identity. Replaying a completed invite never restores
revoked membership.

## count_customers_missing_portal_email [#count_customers_missing_portal_email]

`query` · admin, sales

Count customers without a current portal login email; presence does not imply deliverability or sending

```bash
curl -X POST "$MGR_URL/api/command" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $MGR_TOKEN" \
  -d '{ "breweryId": "00000000-0000-0000-0000-000000000000", "name": "count_customers_missing_portal_email", "input": {} }'
```
