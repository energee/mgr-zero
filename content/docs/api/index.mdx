## Overview [#overview]

MGR has one HTTP endpoint. No resource URLs, no verb shopping. You POST an
operation name and its input, and the response is always the same envelope.
Everything else in this section is a rule that holds across every operation,
or the operations themselves.

### The endpoint [#endpoint]

Registered operations are either queries (side-effect-free reads) or commands
(writes):

```http
POST /api/command
content-type: application/json

{
  "breweryId": "<uuid>",
  "name": "<operation name>",
  "input": { },
  "requestId": "<uuid, commands only>",
  "expectedContext": { "actorId": "<uuid>", "breweryId": "<uuid>", "customerId": "<uuid, portal only>" },
  "origin": "<ui or chat; defaults to ui>",
  "conversationId": "<uuid, chat commands only>",
  "previewToken": "<uuid, chat commands only>"
}
```

`name` and `input` are always required. `breweryId` is required for tenant
operations and must be omitted for `provision_brewery`, the sole authenticated
pre-tenant command. `requestId` is required for
every command and optional for queries. See [idempotency](#idempotency) for why
it exists and what reusing one does.

`expectedContext` is optional for explicit bearer-token clients. The browser app
includes it from the verified context that rendered an action and keeps it with
an uncertain retry. It is a restriction, not identity proof: authentication and
membership checks still decide what the caller may do. When supplied, its actor,
brewery, and optional customer must match the authenticated request before the
operation runs.

`origin` defaults to `ui`. A `chat` command must include both `conversationId`
and `previewToken`. The server issues that token from `preview_command` after it
validates and canonicalizes the proposed input for the signed-in author,
brewery, conversation, and registered write. A token cannot confirm another
input or conversation. Retrying the confirmed command with the same `requestId`
returns its original result even after the preview expires or stock changes and
does not append a second history result. For `record_movement`, the preview
returns signed units, frozen barrel volume, selected bin/lot stock before and
after, displayed SKU/package/location labels, channel tax, destination warnings,
and the lawful correction. Commit locks the inventory ledger and those displayed
dependencies, rebuilds the authoritative snapshot in the same database
transaction, and returns `409 conflict` if anything changed. A stale refusal
leaves no movement, completed request, or conversation result.

The current staff browser composer is a structured client of this same endpoint. It
loads only the registered reads allowed for the current staff role, asks for every
required movement field, calls `preview_command`, and sends `record_movement`
only after the person selects **Commit movement**. Editing or dismissing a
proposal sends no movement command. Staff ATP answers use `get_atp`; portal
domain operations remain limited to the registered `portal_*` surface and no
composer is mounted in the customer shell. Conversation lists and messages are
staff-only, server-owned, author-and-brewery scoped, and contain no credentials
or model transcripts. No model, voice provider, alternate write route, or
client-local conversation history is involved.

The endpoint accepts at most **8 MiB** of JSON per request and admits **120
requests per authenticated account per 60 seconds**. The account budget is
shared by cookie and bearer authentication, every brewery, and the pre-tenant
provisioning command. A `429` response includes `Retry-After` in seconds. The
limit protects this command endpoint; it is not an IP or general Data API
limit. The 5,000-row CSV limit is separate, so imports with unusually large
string cells may need to be split into smaller batches.

### Responses [#responses]

Success carries the operation's result in `data`:

```json
{ "ok": true, "data": { }, "requestId": "…", "correlationId": "…" }
```

Failure carries a code and a message instead:

```json
{ "ok": false, "error": { "code": "not_found", "message": "…" }, "correlationId": "…" }
```

Every response, success or failure, has a server-generated `correlationId`.
Log it. That is the value that ties your client's view of a request to the
server's. A command's response also echoes the `requestId` you submitted, so a
queued write can be matched to its result without keeping the request body
around.

Status codes and every `error.code` are on the [errors page](#errors).

### Calling it [#calling]

Every example in this section uses two variables: `MGR_URL` is the origin the app
is served from (`http://localhost:3000` in development), and `MGR_TOKEN` is a
Supabase access token for a member of the brewery (or any authenticated account
for `provision_brewery`).

```bash
curl -X POST "$MGR_URL/api/command" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $MGR_TOKEN" \
  -d '{ "breweryId": "…", "name": "list_brands", "input": {} }'
```

From the browser the app calls the same endpoint through `lib/commands/client.ts`,
which generates the `requestId` and unwraps the envelope, throwing on failure:

```ts
import { command } from "@/lib/commands/client";

const order = await command(breweryId, "create_order", {
  kind: "wholesale",
  fromLocationId: warehouseId,
  lines: [{ skuId, qty: 10 }],
});
```

The optional sixth argument carries provenance for a confirmed composer write:

```ts
await command(breweryId, "record_movement", input, requestId, expectedContext, {
  origin: "chat",
  conversationId,
  previewToken,
});
```

The customer portal's invoice-payment handoff is a session-authenticated `GET`
instead of a registered operation. It authorizes one current live invoice only
when QuickBooks has reported a positive balance, reads its payment link on the
server, rechecks the balance and access, and redirects without returning or
storing that bearer link in the command API. A zero or unknown current balance
leaves payment unavailable; a reopened invoice with a positive balance remains
eligible even when its history retains an earlier paid date. A reconnect,
credential rotation, or loss of the required accounting permission while the
link is being fetched also leaves payment unavailable.

The public website-menu feed is the other narrow `GET` exception:
`/api/public/menus/{publicId}`. Its opaque id selects one configured POS
location, and the response contains only its location name, a deterministic
`version`,
and explicitly published, currently stocked rows with `brand`, `format`,
`ounces`, `priceCents`, and `available`. It exposes no tenant, catalog, stock,
bin, channel, connection, or provider identifiers. Successful responses set
`Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate=300`;
the quoted version is also its `ETag`, and a matching `If-None-Match` receives
`304` with the same cache headers. Missing ids and failures are not cached. The
endpoint allows cross-origin `GET` and `OPTIONS`, exposes `ETag`, and accepts
`If-None-Match`; its 200, 304, 404, and 503 responses all carry the same safe
wildcard origin policy. It does not accept writes.

Outside the app, the equivalent is a POST with your own `requestId`:

```ts
const requestId = crypto.randomUUID();
const res = await fetch(`${MGR_URL}/api/command`, {
  method: "POST",
  headers: { "content-type": "application/json", authorization: `Bearer ${token}` },
  body: JSON.stringify({ breweryId, name: "create_order", requestId, input }),
});
const { ok, data, error } = await res.json();
```

### Availability [#availability]

Operations are listed by area, each marked with its status. **Available**
operations are registered today and the endpoint answers them. Each one lists
the roles that may call it, its fields, and an example request. **Designed**
operations are ones the screens need that the backend has not built. Calling
one returns `404 unknown_command`.

Both lists are generated from the command registry and from the screens, so
neither can drift from the product. The designed list is the roadmap: what is
coming, and which screen is waiting on it. No dates.

## Authentication & roles [#authentication]

Every request identifies a caller. Tenant operations also identify a brewery. The caller proves who they are
with either the Supabase cookie session the app's login flow establishes, or an
access token:

```bash
curl -X POST "$MGR_URL/api/command" \
  -H 'content-type: application/json' \
  -H "authorization: Bearer $MGR_TOKEN" \
  -d '{ "breweryId": "…", "name": "list_brands", "input": {} }'
```

`provision_brewery` requires authentication but no existing membership; omit
`breweryId`. A dedicated deployment refuses it. Its blank tenant-role cells below mean roles do not apply, not that
access is anonymous. All other operations use the following membership checks.

The `breweryId` in the body then decides *which* brewery the caller is acting
in. Being signed in is not enough. The caller must be a member of that brewery:
staff (`brewery_users` with role `admin`, `sales`, `warehouse`, `brewer` or
`taproom`) or a portal user (`customer_users` linked to one of the brewery's
customers, role `customer`).

The two failures are different, and that difference is worth handling.
`401 unauthenticated` means the token is missing or expired: sign in again.
`403 not_member` means the token is fine and the `breweryId` is wrong.
`409 context_changed` means a supplied `expectedContext` no longer matches;
return to that original account and workspace to retry an uncertain write.

### Roles are enforced twice [#enforcement]

An operation lists the roles that may call it. The endpoint refuses the rest
with `403 permission_denied` before the handler runs. Below that, Postgres
row-level security scopes every query to the caller's brewery, so a role that
slipped through would still read nothing. That matters when you are debugging an
empty result: an empty list and a forbidden read look the same from outside, on
purpose. A caller cannot probe another tenant's data by watching which ids
return `404` rather than `403`.

A portal user sees only their own customer's records. That is why the portal
operations are a separate set, not the staff ones with a filter applied.

## Idempotency & retries [#idempotency]

A network that drops a response has not told you whether the write happened.
Retrying blindly risks a duplicate order. Not retrying risks losing one. The
`requestId` removes the guess.

Every command (every write) must carry a client-generated RFC 9562/4122 UUID as
`requestId`. Queries may omit it. A repeated read costs nothing.

```ts
const requestId = crypto.randomUUID();   // once, before the first attempt

async function submit() {
  return fetch(`${MGR_URL}/api/command`, {
    method: "POST",
    headers: { "content-type": "application/json", authorization: `Bearer ${token}` },
    // The same requestId on every attempt. That is what makes the retry safe.
    body: JSON.stringify({ breweryId, name: "create_order", requestId, input }),
  });
}
```

### The three outcomes [#outcomes]

Reusing a `requestId` with the **identical payload** is the safe retry: the
server recognises the write it already did and answers with the original result
rather than performing it twice.

Reusing one with a **different payload** is `409 conflict`. That is the endpoint
telling you two different writes are wearing the same id. Almost always a
client that generated the id once and then mutated the form.

A **new** `requestId` is a new write, every time. Generating one inside your
retry loop rather than outside it is the single most common way to create
duplicate orders, because each attempt then looks like a fresh intention.

Offline eligibility is narrower than idempotency. The browser currently queues
only `record_fermentation_reading`, after persisting its exact input,
observation time, request ID, actor, brewery, and role before transport. A
reload or reconnect retries that same envelope. `record_movement`,
`record_pick`, and stock transfers require current server state and are never
queued; a stable request ID alone does not make an operation safe offline.

This is not special to the ledger. `set_notification_preference`,
`set_brewery_quiet_hours`, `set_notification_destination`,
`consume_chat_link_proof`, and `unlink_chat_user` claim their `requestId`
against the same caller-and-`requestId`-keyed table every ledger and order RPC
does — there is no separate mechanism: a reused id with a matching payload
replays the original result, and a reused id with a different payload is
`409 conflict`.

### Where to generate it [#where]

Generate the id at the moment the user commits (pressing Submit), not when the
request is built. `lib/commands/client.ts` does exactly this in the app: one id
per invocation, reused by any transport-level retry underneath it.

Timeouts and `5xx` responses are the cases worth retrying, with the same id.
A `4xx` other than `409` will not change on retry. Fix the request instead.

## Errors [#errors]

A failure is the same envelope as a success, with `ok: false`:

```json
{
  "ok": false,
  "error": { "code": "conflict", "message": "requestId reused with a different payload" },
  "requestId": "11111111-1111-1111-1111-111111111111",
  "correlationId": "…"
}
```

Branch on `code`, never on `message`. The code is a contract. The message is
written for a person and will be reworded. Both are safe to show a user. The
endpoint never returns raw database text, which is why an unmapped database
failure arrives as a generic `db_error` while the detail goes to the server log
under the same `correlationId` you were given.

Every response carries a `correlationId`, success or failure. Log it. It is the
one value that ties what your client saw to what the server recorded.

### Validation failures name their fields [#validation]

`invalid_input` messages are generated from the operation's schema, one line per
problem:

```
validation failed: ✖ Invalid UUID → at customerId
```

So a 400 is usually actionable without reading anything else. Each operation's
field table lists the same types the validator enforces.

## Conventions [#conventions]

These hold across every operation, so they are stated once here rather than
repeated in each field table.

**Field names are camelCase** in `input`, even though the database columns they
land in are snake_case. Response payloads come back in the database's own shape,
so a field you send as `skuId` reads back as `sku_id`. That asymmetry is real.
Handle it in one mapping layer rather than at each call site.

**Ids are UUIDs** wherever the id belongs to MGR: every record you create, read,
or reference here. The exception is an id minted by somebody else and stored as
it arrives. `externalDestinationId` on `set_notification_destination` is a Slack
channel id, and its field table says `string` for that reason. Read the table
when it disagrees with this line. The table is generated from the schema. This
sentence is not.

**Money is integer cents.** `unitPriceCents: 1250` is $12.50. There are no
floats in prices anywhere in the API, because a fraction of a cent that survives
a few multiplications becomes a discrepancy on an invoice.

**Dates are `YYYY-MM-DD` strings**, not timestamps, wherever the field means a
calendar day. A requested ship date is a day, not an instant. Fields that
genuinely mean an instant, such as `now` on `get_today`, take an offset-aware
ISO timestamp so the server never has to guess a timezone.

**Most volumes are plain numbers; one takes an exact decimal string.**
`bblPerUnit` on `upsert_format` is a JSON number, like `0.1651`. `reattribute_loss`'s
`bbl` is the exception: it accepts either a number or a string such as
`"0.1651"`, because that figure feeds excise reporting and binary floating
point cannot represent most decimal fractions exactly. A string there keeps
the exact decimal the brewery entered all the way to the tax form. Check each
operation's field table rather than assuming a volume field takes a string.

**`limit` defaults to 50 and caps at 200** on every operation that takes one.

### Fields the server computes [#computed]

Some values are derived and must not be sent. `bbl` on an inventory movement is
computed from the SKU and the quantity. A field an operation does not declare is
dropped before the handler runs rather than trusted, so sending your own `bbl`
does not fail. It is simply ignored, because two sources for one number is how
ledgers drift. Read the computed value back rather than assuming yours was used.
`create_composed_format`, `publish_pos_item`, `publish_pos_menu`, and
`record_fermentation_reading` are the exception: their schemas refuse an
undeclared field outright with `400 invalid_input` instead of dropping it.

Prices on order lines are snapshotted at creation from the customer's price
group. You do not send them, and changing a price group later does not rewrite
an existing order.

### Nothing is edited in place [#append-only]

The inventory ledger is append-only: a correction is a new movement in the
opposite direction, never an edit. Invoices work the same way. A credit memo is
negative lines at the original prices. Where you might expect an update or a
delete, look for the compensating operation instead.
