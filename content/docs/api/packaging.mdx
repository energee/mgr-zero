---
title: "Packaging"
description: "Packaging runs, formats and their bills of material, repacks."
---

A format is a packaging configuration: what a SKU is filled into and what that
consumes. Its bill of material is replaced wholesale rather than patched line by
line, so a partially edited BOM never exists.

A packaging run is scheduled, then closed with what it actually produced and
consumed. Closing is the step that moves beer out of a vessel and finished goods
into inventory. Before scheduling, `get_packaging_material_plan` previews
material needs and stock shortages for unsaved output quantities.

Scheduling and replacing planned outputs require whole `qtyPlanned` values for
formats whose `package_type` is `keg`. Other package types may retain fractional
quantities. This rule uses saved format metadata, not package names, and rejects
fractions before storage rounding. Completed requests replay their original
results before the new rule is checked; changed raw payloads still conflict.
Scheduling needs no source tank, and a past planned date or a plan larger than
its selected source remains legal. Planning does not reserve or move inventory.

Closing a run requires confirmed material `actuals` and the `planRevision` returned by `get_packaging_close_plan`; a plan that changed since then is refused with `409 stale_plan`. Omit them only to replay an already completed pre-upgrade request with its original request ID. Used plus lost quantities debit explicit sources; unused is an observation. The close stores the reviewed BOM and actuals atomically with outputs and tank draw. `correct_packaging_material_record` appends exact material reversals and replacement actuals, without changing finished output or tank volume. Downstream finished-goods use, completed batches and dependent filed reports prevent correction.

Each new close requires nonnegative, finite `bblDrawn` and rounds it to three decimals for storage and comparison with the sum of frozen `production_in` movement barrels. The original input remains part of request identity: different raw draws conflict under the same request ID even if they round alike. Completed requests replay before this validation. Output exceeding draw by more than **0.0005 bbl** is refused with `400 bad_request`; equality and excess up to that tolerance are accepted. Tank availability uses the same tolerance, while the batch-total guard still rejects any negative residual. A rejection rolls back the entire close, including its request claim, lot, output quantities and movements, material records and consumption. Correct the draw or package counts before submitting again.

`correct_packaging_run_outputs` corrects a closed run without reopening it. First read `get_packaging_output_corrections`; pass its latest correction ID as `previousCorrectionId`, or null for the first correction. It atomically appends exact, frozen `production_in` reversals and replacement production, replaces the run's actual output pointers and barrels drawn, and records the reason, actor, previous quantities and replacement quantities. The lot, packaged date, planned outputs and material actuals stay unchanged. Supply only planned SKUs; omitted outputs become zero. Non-keg quantities round to two decimals, and history records the same applied quantities for every planned SKU, sorted by SKU ID. Retain the original finished-goods location and bin if the run has produced stock; otherwise choose a valid location and bin. Whole-keg, finite nonnegative count and draw, tank availability, draw conservation and batch-total guards apply. Downstream finished-goods use, completed batches, dependent filed reports and stale revisions are refused. Stockless historical runs cannot use it. Identical requests replay exactly; changed raw input under the same request ID conflicts even when quantities round alike. Its production reversals retain the original packaged date and classification, so lot balances, completion and unfiled compliance read the corrected production rather than an inventory adjustment.

The corrected draw rounds to three decimals before storage. Its stored value cannot exceed the available source-tank volume after restoring this run's current draw; an input that rounds up beyond that volume is refused atomically. The original raw-input availability guard and request identity still apply, so sub-precision input remains valid when its stored draw fits.

A source occupancy ended by a cellar transfer cannot have its stored `bblDrawn` reduced. That would restore inaccessible beer into the ended tank stay. Correcting output quantities while retaining the draw remains allowed, subject to the other guards.
