---
title: "Purchasing & materials"
description: "Materials, vendors and purchase orders."
---

Materials are what the brewery buys rather than sells: grain, hops, cans, crowns,
labels. They carry their own on-hand and their own counts, separate from the
finished-goods ledger, because a shortfall in either stops a run for different
reasons.

A purchase order is drafted (optionally from computed material requirements),
sent to a vendor, then received. Receiving is what writes material stock, so an
unreceived PO never inflates what a packaging run believes it has.

`receive_purchase_order` and `correct_purchase_receipt` require finite,
nonnegative counts with at most four decimal places in purchase units.
The count multiplied by the receipt's purchase-unit conversion must also fit
four decimal places in base units. An overprecise count is refused atomically,
not rounded independently in the receipt and material ledger. For the same
reason `upsert_material` keeps `purchaseUomFactor` to four decimal places
(the `materials` table checks it too), so a whole-unit count always converts
exactly.

Each line of `receive_purchase_order` and `correct_purchase_receipt` accepts
optional `unitCostCents`: integer cents per purchase unit from 0 to 2147483647.
Omitting it keeps the ordered price on receive or the frozen receipt price on
correction. Supplying it records the actual receipt price and derives the
movement's cost per base unit using the receipt conversion. It does not rewrite
the sent PO or an original receipt. Correction still requires a reason and must
preserve nonnegative stock and lot provenance; post the latest priced receipt's
Bill after a missing cost is fixed.

An order that will not arrive in full is closed with a reason. A draft or sent
order with no receipts is cancelled (`cancel_purchase_order`); one with at
least one receipt is closed short (`close_purchase_order_short`), which keeps
the received stock and releases only the unreceived remainder. Each call is
refused for the other case, and the actor and time are recorded with the reason.

`get_material_requirements` returns one row per material. `required` includes
firm demand and projected packaging; `projected` is the projected part in the
material's base units. Order projection nets finished goods, open run outputs
and projected batch packages against open order allocations. Standing
allocations hold stock but never project alone. Order `needed_by` is the
earliest open requested ship date, falling back to today. Batch projection
uses each active SKU's default volume share and the brewery's days-to-package
estimate. A non-cancelled run linked directly or through its source occupancy
replaces the entire batch projection, even after the run closes. An unlinked
tankless run cannot replace a particular batch. Projected shortfalls draft
with the same vendor, lead-time and whole-purchase-unit rules as firm demand.

`set_qbo_vendor_mapping` accepts the vendor's exact QuickBooks ID and
`set_qbo_purchase_account` sets one expense or inventory asset account for all
materials. Both require Admin and a connected company. A different company
clears these mappings. There is no vendor-name matching or per-material account.

Admin calls `post_receipt_bill` with a saved `receiptId`. It creates one Bill
for that receipt revision chain, never a QuickBooks purchase order. Positive
receipt lines use the frozen movement's base quantity times `unit_cost_cents`,
rounded to cents per line. Missing vendor/account mappings or recorded costs
block the first attempt before a provider request is reserved.

The first call persists the exact payload, company, and provider request ID
before its single POST. Success returns `{ receiptId, status: "pushed", remoteId }`.
Every retry first reconciles by the frozen document number and request marker.
An exact match records the existing Bill; an empty query replays the identical
payload and provider request ID, using Intuit's documented idempotence guarantee.
An ambiguous identity or unsuccessful lookup never authorizes a POST.
A definite rejection records `push_failed`; after fixing mappings, explicitly
send `newAttemptReason: "corrected"` with a new command request ID to freeze a
new attempt. A pending uncertain request cannot use that option.
Mapping changes cannot rewrite a reserved request.
`get_purchase_order` includes each receipt's `qbo_bill_id`, `qbo_bill_request_id`,
`qbo_bill_status`, `qbo_bill_error`, and canonical `qbo_bill_receipt_id`.
Its `vendor` carries `qbo_vendor_id` and `qbo_realm_id`, so a caller can check
the vendor mapping without listing every vendor.

Correcting a receipt after an attempt preserves that payable identity and
payload. Posted corrections must be adjusted in QuickBooks, not by another Bill
or vendor credit. Bill payments are QuickBooks-only and are not included in
`sync_qbo_payments`. Reconnecting another company cannot retarget a pending Bill; after a definitive
rejection, `newAttemptReason: "corrected"` posts to the currently connected company.
