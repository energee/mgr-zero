Staff roles are `admin`, `sales`, `warehouse`, `brewer` and `taproom`. A member
can hold several roles and receives every permission allowed by any of them.
Every operation in this reference lists the roles allowed to call it. Staff
roles never grant customer-portal membership. Revoking a brewery membership
ends its access without deleting the history that member wrote.

`list_team_members` returns `{ userId, name, email, roles, createdAt }` for each
member. `name` is the saved Auth profile full name with the account email beside
it, as `Profile name <email>`, or the full email address alone when no nonblank
name is saved. Profile names are display-only and never grant permissions.
`update_staff_role` replaces a member's roles with the nonempty `roles` array
in its input; duplicate values are removed and the response uses enum order.
Removing `admin` is a demotion even when other roles remain, and is refused
when it would leave the brewery without an admin. A request that sends `role`
without `roles` fails with `400 invalid_input`; an extra `role` key beside
`roles` is ignored. `invite_staff` still grants one role; an admin can add
others afterward.

`invite_staff` assigns one role; `invite_customer_user` links one customer. An
email with no confirmed Auth account is sent an Auth invitation and the
command returns `{ userId }` once membership completes. An email that already
has a confirmed Auth account instead gets a pending invitation: the command
returns `{ inviteId, state: "pending_consent" }`, and membership is granted
only when that account's owner signs in and calls
`accept_account_invitation`; consent expires after seven days. Invitation
requests retain their Auth identity through interrupted completion; retry
unchanged requests with the same ID. Changing the email, role, customer,
actor, or brewery is different intent. Completed replay does not restore
revoked membership. The inviter must still have permission when membership is
completed, including at consent time for a pending invitation.

`list_my_invitations` and `accept_account_invitation` omit `breweryId`; they
act on the signed-in caller's own pending invitations, not a named brewery.
`accept_account_invitation` returns `{ breweryId, kind, customerId }`
(`customerId` is `null` for a staff invitation); replay after the granted
membership is later removed does not restore it, and a new invitation is
required. `revoke_account_invitation` returns `{ inviteId }` and only affects
an invitation still `pending_consent`.

`list_pending_invitations` returns the brewery's staff invitations still
`pending_consent` and not expired: `{ id, email, role, createdAt }`, oldest
first. A new-account invitation never appears: its membership is granted
when the Auth invitation is sent. `resend_account_invitation` takes the
`inviteId` of a `pending_consent` invitation. It revokes that invitation and
returns `{ inviteId }` for a new one with the same email and role, sent by
the caller, with a fresh seven-day consent window. Only the new invitation
can be accepted. Replaying the same request ID returns the same new
`inviteId`.

`provision_brewery` omits `breweryId`; authenticated callers send name, a valid
timezone, and optional `ttb`. One transaction creates the brewery and first
admin membership and returns the brewery UUID. Replay returns that UUID without
restoring revoked membership. `MGR_DEDICATED=1` refuses brewery creation from
the web and the API alike with `403 permission_denied`.

`import_csv` accepts 1–5000 string-field rows and returns
`{ committed, blocked, outcomes }`. Each outcome names its 1-based `row`,
`status` (`committed` or `blocked`), and its original `result` or `error`.
Dependent writes within one row commit together; independent rows may succeed
when another fails. Both successful and blocked outcomes are durable: resend
the identical kind and complete rows array with the same request ID to recover
the original results. Changed, appended, or removed rows conflict. Start a new
request containing only corrected blocked rows; posting committed opening
balances with a new ID adds stock again.

All import values are strings. Required fields precede the semicolon:

| Kind | Fields |
| --- | --- |
| `customers` | `name`, `type`, `state`, `saleChannelId`; `licenseNumber`, `paymentTerms` |
| `ship_tos` | `customerId`, `label`, `address1`, `city`, `zip`, `state`; `address2` |
| `products_skus` | `product`, `formatId`; `sku_name`, `style`, `abv`, `upc` |
| `channel_prices` | `saleChannelId`, `priceGroupId`, `formatId`, `unitPriceCents` |
| `opening_balances` | `skuId`, `locationId`, `binId`, `qty`; `note` |

Unknown row fields are rejected. Reference ID fields accept either an existing
UUID or a trimmed, case-insensitive exact record name. Missing or ambiguous names
block the row; use the UUID to distinguish duplicate names. Bin names resolve
within the row's location; pour formats resolve within its price group. Product
imports accept packaged formats only. Create missing references before importing.
Raw cell strings remain part of request identity; replacing a name with its UUID
is changed input, not an unchanged retry. Channel-price files run in file order
when a reference column mixes UUIDs and names; the final row wins when several
rows target the same cell. Product imports reuse an existing brand without
changing its metadata and create the SKU in the same row transaction. Duplicate
customer/SKU creation is blocked; channel-price rows set the existing grid cell.
Opening quantities are positive SKU-unit quantities with a bin belonging to the
location. Prices are nonnegative integer cents, at most 2147483647.
